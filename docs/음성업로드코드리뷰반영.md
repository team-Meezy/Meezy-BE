# 음성 업로드 코드리뷰 반영 보고서

음성 업로드 성능 개선 PR에 대한 코드리뷰(CodeRabbit)에서 지적된 문제점과 해결 방법을 정리한다.

---

## 1. gradle.properties 하드코딩된 JDK 경로

### 문제점

`gradle.properties`에 Windows 전용 JDK 경로가 하드코딩되어 커밋됨.

```properties
org.gradle.java.home=C:/Program\ Files/Eclipse\ Adoptium/jdk-21.0.9.10-hotspot
```

다른 개발자 환경, CI/CD, Docker에서 빌드가 실패하는 원인이 된다.

### 해결

- `gradle.properties`를 Git 추적에서 제거 (`git rm --cached`)
- `.gitignore`에 `gradle.properties` 추가
- JDK 경로는 각 개발자의 로컬 `~/.gradle/gradle.properties` 또는 `JAVA_HOME` 환경변수로 관리

## 2. ReportGenerationStressSimulation 상태 코드 불일치

### 문제점

`MeetingController`가 녹음 업로드에 대해 HTTP 202(Accepted)를 반환하도록 변경되었으나, `ReportGenerationStressSimulation`의 체크는 여전히 200을 기대하고 있었다.

```java
// 변경 전 (잘못됨)
.check(status().in(200, 500))
```

이로 인해 정상 요청도 실패로 집계되어 스트레스 테스트 결과가 무효화된다.

### 해결

```java
// 변경 후
.check(status().in(202, 500))
```

## 3. 보상 삭제(S3) 예외 미처리

### 문제점

`RecordingAsyncProcessor`에서 DB 저장이 실패한 후 보상 트랜잭션으로 S3 파일을 삭제하는데, 이 삭제 자체가 실패하면 예외가 전파되어 외부 catch로 빠지면서 원래 DB 에러 정보가 사라진다. S3에는 고아 파일이 남게 된다.

```java
// 변경 전
} catch (Exception e) {
    log.error("녹음 DB 저장 실패, S3 파일 삭제: key={}", s3Key, e);
    audioStoragePort.deleteAudio(s3Key);  // 이것도 실패하면?
}
```

### 해결

보상 삭제에 별도 try/catch를 추가하여, 삭제 실패 시에도 고아 파일 발생을 로그로 추적할 수 있도록 했다.

```java
// 변경 후
} catch (Exception e) {
    log.error("녹음 DB 저장 실패, S3 파일 삭제: key={}", s3Key, e);
    try {
        audioStoragePort.deleteAudio(s3Key);
    } catch (Exception deleteEx) {
        log.error("S3 보상 삭제 실패 (고아 파일 발생): key={}", s3Key, deleteEx);
    }
}
```

## 4. TOCTOU 인가 갭 (Time-of-Check to Time-of-Use)

### 문제점

`validateMeetingOwnership()`과 `saveRecording()`이 별도 트랜잭션에서 실행된다. 검증과 저장 사이에 S3 업로드(수십 초)가 있으므로, 그 사이에 회의가 삭제되거나 팀 소속이 변경될 수 있다.

```text
validateMeetingOwnership()  →  S3 업로드 (수십 초)  →  saveRecording()
│── TX1 (readOnly) ──────│                          │── TX2 ─────────│
                              ↑ 이 사이에 데이터 변경 가능
```

기존 `saveRecording()`은 `meetingId`로만 조회하여 팀 소속 재검증 없이 저장했다.

### 해결

`saveRecording()`에 `teamId` 파라미터를 추가하고, 저장 직전에 팀 소속을 재검증하도록 했다.

```java
// 변경 전
@Transactional
public void saveRecording(UUID meetingId, String s3Key) {
    Meeting meeting = meetingRepository.findByMeetingId_Value(meetingId)
            .orElseThrow(MeetingNotFoundException::new);
    meeting.receiveRecording(s3Key);
    meetingRepository.save(meeting);
    // ...
}

// 변경 후
@Transactional
public void saveRecording(UUID teamId, UUID meetingId, String s3Key) {
    Meeting meeting = meetingRepository.findByMeetingId_Value(meetingId)
            .orElseThrow(MeetingNotFoundException::new);
    meeting.validateBelongsToTeam(TeamId.of(teamId));  // 재검증
    meeting.receiveRecording(s3Key);
    meetingRepository.save(meeting);
    // ...
}
```

## 5. 비동기 작업 거부 시 녹음 유실

### 문제점

기존 `AsyncConfig`의 거부 정책이 로그만 남기고 작업을 버리는 방식이었다.

```java
// 변경 전
executor.setRejectedExecutionHandler((runnable, pool) ->
    log.warn("비동기 작업 거부됨: 큐 가득 참"));
```

큐(500)가 가득 차면 녹음이 조용히 유실된다. 클라이언트는 202를 받았지만 실제로는 처리되지 않는다. 임시 파일도 삭제되지 않고 디스크에 남는다.

### 해결

`CallerRunsPolicy`로 변경하여, 큐가 가득 차면 호출 스레드(HTTP 요청 스레드)가 직접 작업을 실행하도록 했다.

```java
// 변경 후
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
```

이 정책의 효과:
- **작업 유실 방지**: 거부되는 작업이 없으므로 녹음이 유실되지 않음
- **자연스러운 Back-pressure**: 큐가 가득 차면 호출 스레드가 블로킹되어 새로운 요청 수용 속도가 자동으로 느려짐
- **트레이드오프**: 극단적 부하 시 일부 요청의 응답이 느려질 수 있지만, 데이터 유실보다는 낫다

## 6. 잘못된 요청에 HTTP 202 반환 (인지된 트레이드오프)

### 문제점

`validateMeetingOwnership()`이 비동기 경로로 이동했으므로, 존재하지 않는 teamId/meetingId로 요청해도 HTTP 202가 반환된다. 클라이언트가 에러를 즉시 알 수 없다.

### 현재 대응

이 문제는 **성능과 정합성 사이의 의도된 트레이드오프**로 인지하고 있다.

- 비동기 경로에서 검증 실패 시 에러 로그로 추적
- 실제 서비스에서 녹음 업로드는 회의 진행 중에만 발생하므로, 잘못된 ID가 전달될 가능성이 매우 낮음
- 추후 개선 방안: Redis 캐시에 활성 회의 ID를 저장하고, 동기 경로에서 캐시 기반으로 가볍게 검증
