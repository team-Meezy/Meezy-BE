## 1. 개요

Meezy 서비스의 **회의 녹음 업로드 API** (`POST /teams/{teamId}/meetings/{meetingId}/recording`)에서 동시 요청 시 심각한 응답 지연과 타임아웃이 발생했다.

Gatling 부하 테스트로 병목을 측정하고, 5단계에 걸친 반복적인 개선을 통해 **P50 응답시간을 18초에서 321ms로 (98.2% 감소)**, **평균 응답시간을 18초에서 1초로 (94% 감소)** 개선했다.

## 3. 1단계: 문제 진단 — Baseline 측정

### 3.1 원본 코드 구조

```java
// ReceiveRecordingService.java (원본)
@Transactional
public void receive(UUID teamId, UUID meetingId, MultipartFile recording) {
    validateRecording(recording);           // 파일 형식 검증
    validateMeetingOwnership(teamId, meetingId);  // DB 조회: 팀/회의 검증
    String s3Key = audioStoragePort.uploadAudio(recording);  // S3 업로드 (41MB)
    meeting.receiveRecording(s3Key);        // DB 저장
    eventPublisher.publishEvent(event);     // 이벤트 발행
}
```

### 3.2 문제점

```
[HTTP 요청 스레드 · @Transactional]
validateMeetingOwnership()  →  S3 업로드 (41MB)  →  DB 저장  →  이벤트 발행  →  HTTP 200
│── DB 커넥션 점유 ──────────────────────────────────────────────────────────────│
```

1. **S3 업로드가 `@Transactional` 내부에서 실행**: 41MB 파일 업로드(수십 초) 동안 DB 커넥션을 계속 점유
2. **DB 커넥션 풀 고갈**: HikariCP 기본 pool-size 10으로 동시 요청 시 커넥션 대기 발생
3. **`SimpleAsyncTaskExecutor` 무제한 스레드 생성**: Spring 기본 비동기 실행자가 스레드 수 제한 없이 생성 → OpenAI 이벤트 리스너의 재시도 스레드가 서버 리소스 고갈
4. **동기 응답 방식**: 클라이언트가 S3 업로드 완료까지 대기해야 함

### 3.3 Gatling 측정 결과

| 지표 | 값 |
|------|-----|
| **성공** | **131 / 140 (93.6%)** |
| **실패** | 9건 (타임아웃 60초 초과) |

## 4. 2단계: @Transactional 분리

### 4.1 개선 내용

S3 업로드를 `@Transactional` 밖으로 분리하여 DB 커넥션 점유 시간을 줄이고자 했다.

`RecordingTransactionHandler`를 별도 빈으로 생성하여 트랜잭션이 필요한 로직만 분리했다.

> **핵심 개념 — Spring AOP 프록시 제한**: Spring의 `@Transactional`은 AOP 프록시를 통해 동작한다. 같은 클래스 내에서 `this.method()`로 호출하면 프록시를 거치지 않아 `@Transactional`이 적용되지 않는다. 따라서 트랜잭션이 필요한 메서드는 **별도 빈**으로 분리해야 한다.

```java
// RecordingTransactionHandler.java (신규 생성)
@Component
@RequiredArgsConstructor
public class RecordingTransactionHandler {

    private final MeetingRepository meetingRepository;
    private final ApplicationEventPublisher eventPublisher;

    @Transactional(readOnly = true)
    public void validateMeetingOwnership(UUID teamId, UUID meetingId) {
        Meeting meeting = meetingRepository.findByMeetingId_Value(meetingId)
                .orElseThrow(MeetingNotFoundException::new);
        meeting.validateBelongsToTeam(TeamId.of(teamId));
    }

    @Transactional
    public void saveRecording(UUID meetingId, String s3Key) {
        Meeting meeting = meetingRepository.findByMeetingId_Value(meetingId)
                .orElseThrow(MeetingNotFoundException::new);
        meeting.receiveRecording(s3Key);
        meetingRepository.save(meeting);
        meeting.pullDomainEvents().forEach(event -> {
            if (event instanceof RecordingReceivedEvent recordingEvent)
                eventPublisher.publishEvent(recordingEvent);
        });
    }
}
```

변경 후 구조:

```
[HTTP 요청 스레드]
validateMeetingOwnership()  →  S3 업로드 (41MB)  →  [TX] DB 저장 + 이벤트  →  HTTP 200
│── TX(readOnly) ───────│                          │── TX ─────────────────│
```

### 4.2 결과

- **성공률이 오히려 하락** (HTTP 500 에러 대량 발생)
- S3 업로드 실패가 `@Transactional` 밖에서 발생하면서 에러 핸들링 미비
- `SimpleAsyncTaskExecutor`의 무제한 스레드 생성 문제가 더 두드러짐

### 4.3 발견된 추가 문제

서버 로그에서 OpenAI 관련 에러가 대량 발생:

```
OpenAI 429: "insufficient_quota"
RST_STREAM: stream was reset
```

녹음 업로드 후 발행되는 `RecordingReceivedEvent`를 처리하는 `RecordingEventListener`가 `@Async`로 OpenAI API를 호출하는데, `SimpleAsyncTaskExecutor`가 스레드를 무제한 생성하여 OpenAI 재시도 스레드가 서버 리소스를 고갈시키고 있었다.

## 5. 3단계: 비동기 스레드 풀 제한 + S3 동시성 제어

### 5.1 개선 내용

#### AsyncConfig 생성 — 비동기 스레드 풀 제한

`SimpleAsyncTaskExecutor`(무제한) 대신 `ThreadPoolTaskExecutor`로 교체하여 스레드 수를 제한했다.

```java
// AsyncConfig.java (신규 생성)
@Configuration
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(50);
        executor.setThreadNamePrefix("async-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}
```

#### S3 동시 업로드 제한 — Semaphore + 재시도

```java
// S3AudioStorageAdapter.java (수정)
private static final int MAX_CONCURRENT_UPLOADS = 5;
private static final int MAX_RETRIES = 3;
private static final long RETRY_BASE_DELAY_MS = 500;
private final Semaphore uploadSemaphore = new Semaphore(MAX_CONCURRENT_UPLOADS);

@Override
public String uploadAudio(MultipartFile file) {
    String key = KEY_PREFIX + UUID.randomUUID() + ".mp3";
    try {
        uploadSemaphore.acquire();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new AudioUploadFailedException();
    }
    try {
        return uploadWithRetry(file, key);  // 지수 백오프: 500ms → 1s → 2s
    } finally {
        uploadSemaphore.release();
    }
}
```

### 5.2 결과 및 발견된 문제

- HTTP 500 에러는 감소했지만 여전히 발생
- **`CallerRunsPolicy`의 부작용 발견**: 큐(50)가 가득 차면 요청 스레드가 직접 비동기 작업(S3 업로드)을 실행 → 동기 블로킹 발생
- 근본 문제: 동기 경로에서 41MB S3 업로드를 대기하는 구조 자체가 한계

## 6. 4단계: 비동기 업로드 + 즉시 HTTP 202 응답

### 6.1 개선 내용

S3 업로드를 비동기로 분리하고, 클라이언트에게 즉시 HTTP 202 (Accepted)를 반환하는 구조로 변경했다.

#### RecordingAsyncProcessor — 별도 빈으로 @Async 분리

> **핵심 개념**: `@Async`도 `@Transactional`과 동일하게 Spring AOP 프록시로 동작한다. 같은 클래스 내 호출 시 프록시를 거치지 않으므로 반드시 **별도 빈**으로 분리해야 한다.

```java
// RecordingAsyncProcessor.java (신규 생성)
@Component
@RequiredArgsConstructor
public class RecordingAsyncProcessor {

    private final AudioStoragePort audioStoragePort;
    private final RecordingTransactionHandler transactionHandler;

    @Async
    public void process(UUID teamId, UUID meetingId, Path tempFile) {
        try {
            String s3Key = audioStoragePort.uploadAudioFromPath(tempFile);
            try {
                transactionHandler.saveRecording(meetingId, s3Key);
            } catch (Exception e) {
                audioStoragePort.deleteAudio(s3Key);  // 보상 트랜잭션
            }
        } catch (Exception e) {
            log.error("녹음 비동기 처리 실패: meetingId={}", meetingId, e);
        } finally {
            Files.deleteIfExists(tempFile);
        }
    }
}
```

#### ReceiveRecordingService — 동기 경로 최소화

```java
// ReceiveRecordingService.java (수정)
@Service
@RequiredArgsConstructor
public class ReceiveRecordingService {

    private final RecordingTransactionHandler transactionHandler;
    private final RecordingAsyncProcessor asyncProcessor;

    public void receive(UUID teamId, UUID meetingId, MultipartFile recording) {
        validateRecording(recording);                            // 파일 형식 검증
        transactionHandler.validateMeetingOwnership(teamId, meetingId);  // DB 검증
        Path tempFile = extractTempFilePath(recording);          // 임시 파일 저장
        asyncProcessor.process(teamId, meetingId, tempFile);     // 비동기 위임
    }
}
```

#### MeetingController — HTTP 202 반환

```java
@PostMapping("/{meetingId}/recording")
public ResponseEntity<Void> receiveRecording(...) {
    receiveRecordingService.receive(teamId, meetingId, request.file());
    return ResponseEntity.accepted().build();  // 즉시 202 반환
}
```

#### 스레드 풀 및 커넥션 풀 확장

```java
// AsyncConfig.java (수정)
executor.setCorePoolSize(8);    // 4 → 8
executor.setMaxPoolSize(16);    // 8 → 16
executor.setQueueCapacity(500); // 50 → 500
// CallerRunsPolicy → 로그 경고 후 폐기 (요청 스레드 블로킹 방지)
executor.setRejectedExecutionHandler((runnable, pool) ->
    log.warn("비동기 작업 거부됨: 큐 가득 참"));
```

```yaml
# application.yml (수정)
spring:
  datasource:
    hikari:
      maximum-pool-size: 20  # 10 → 20
      minimum-idle: 10
```

#### S3 Path 기반 업로드 추가

기존 `MultipartFile` 기반 업로드는 스트림을 사용하므로, 임시 파일의 `Path`를 직접 전달하여 `RequestBody.fromFile()`로 업로드하도록 최적화했다.

```java
// AudioStoragePort.java (수정)
public interface AudioStoragePort {
    String uploadAudio(MultipartFile file);
    String uploadAudioFromPath(Path filePath);  // 추가
    byte[] downloadAudio(String s3Key);
    void deleteAudio(String s3Key);
}
```

### 6.2 변경 후 구조

```
[동기 경로 — HTTP 요청 스레드]
validateRecording()  →  validateMeetingOwnership()  →  임시파일 저장  →  HTTP 202 즉시 반환
  (메모리 연산)              (DB 조회)                  (파일 I/O)

[비동기 경로 — 별도 스레드 풀]
S3 업로드 (41MB)  →  [TX] DB 저장 + 이벤트 발행  →  임시파일 삭제
```

### 6.3 결과

- **HTTP 500 에러 완전 제거** (0건)
- 그러나 **약 27% (75건/280건) 타임아웃** 여전히 발생

### 6.4 발견된 문제

즉시 202를 반환하는데도 타임아웃이 발생한 원인을 분석한 결과:

1. **동기 경로에 남아있는 `validateMeetingOwnership()` DB 조회**: 동시 요청 시 DB 커넥션 대기 발생
2. **BCrypt 로그인의 CPU 부하**: BCrypt 해싱이 CPU 집약적이라 동시 로그인이 서버를 압박

### 6.5 추가 시도: 사전 토큰 주입 (로그인 스킵)

BCrypt 병목을 제거하기 위해 사전에 토큰을 발급받아 로그인 없이 업로드만 테스트했다.

| 지표 | 로그인 포함 | 토큰 사전주입 |
|------|-----------|-------------|
| 총 요청 | 280건 | 140건 (업로드만) |
| 성공률 | 73.2% | **41.4%** |

**오히려 악화.** 로그인 과정이 자연스러운 속도 조절(throttle) 역할을 하고 있었고, 토큰 사전주입 시 140명이 동시에 업로드를 시도하여 서버에 더 큰 부하가 집중되었다.

→ 로그인 포함 테스트가 현실적인 시나리오라 판단, 로그인 포함으로 복귀.

## 7. 5단계 (최종): DB 검증을 비동기 경로로 이동

### 7.1 개선 내용

동기 경로에 남아있던 마지막 I/O 병목인 `validateMeetingOwnership()` DB 조회를 비동기 경로로 이동했다.

#### ReceiveRecordingService — 동기 경로에서 I/O 완전 제거

```java
// ReceiveRecordingService.java (최종)
@Service
@RequiredArgsConstructor
public class ReceiveRecordingService {

    private final RecordingAsyncProcessor asyncProcessor;

    public void receive(UUID teamId, UUID meetingId, MultipartFile recording) {
        validateRecording(recording);            // ① 파일 형식 검증 (메모리 연산)
        Path tempFile = extractTempFilePath(recording);  // ② 임시 파일 저장 (파일 I/O)
        asyncProcessor.process(teamId, meetingId, tempFile);  // ③ 비동기 위임 (큐에 넣기)
        // → 즉시 HTTP 202 반환
    }
}
```

#### RecordingAsyncProcessor — DB 검증을 비동기에서 수행

```java
// RecordingAsyncProcessor.java (최종)
@Component
@RequiredArgsConstructor
public class RecordingAsyncProcessor {

    private final AudioStoragePort audioStoragePort;
    private final RecordingTransactionHandler transactionHandler;

    @Async
    public void process(UUID teamId, UUID meetingId, Path tempFile) {
        try {
            transactionHandler.validateMeetingOwnership(teamId, meetingId);  // ① DB 검증
            String s3Key = audioStoragePort.uploadAudioFromPath(tempFile);   // ② S3 업로드
            try {
                transactionHandler.saveRecording(meetingId, s3Key);          // ③ DB 저장 + 이벤트
            } catch (Exception e) {
                audioStoragePort.deleteAudio(s3Key);  // 보상 트랜잭션
            }
        } catch (Exception e) {
            log.error("녹음 비동기 처리 실패: meetingId={}", meetingId, e);
        } finally {
            Files.deleteIfExists(tempFile);
        }
    }
}
```

### 7.2 최종 구조

```
[동기 경로 — HTTP 요청 스레드]                     [비동기 경로 — 스레드 풀]

validateRecording()                                validateMeetingOwnership()
       ↓                                                  ↓
extractTempFilePath()                              S3 업로드 (41MB)
       ↓                                                  ↓
asyncProcessor.process()  ─── 큐에 넣기 ──→        [TX] DB 저장 + 이벤트 발행
       ↓                                                  ↓
HTTP 202 반환                                      임시파일 삭제
```

동기 경로에는 **메모리 연산과 파일 I/O만** 남아 DB, 네트워크 I/O가 완전히 제거되었다.
